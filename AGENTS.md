# bilbo

## Testing

- Read `docs/testing.md` before adding or moving a test.
- `nix develop -c bazel test //...` runs every layer except tests that need the screen (`desktop`) and release.
- `--config=<layer>` runs one layer (`unit`, `contract`, `acceptance`, `integration`, `snapshot`, `e2e`, `release`); `--config=desktop` runs only screen tests; `--config=all` runs everything. Desktop tests take focus and keyboard input. A layer config also runs that layer's desktop tests: add `--test_tag_filters=<layer>,-desktop` to stay headless.
- Every run of the built binary, by hand or in a test, sets `BILBO_HOME`, `XDG_STATE_HOME` and `XDG_CACHE_HOME` to scratch folders and `BILBO_CONFIG` to a scratch `config.toml` that exists, empty or not: `BILBO_HOME` moves only the store, and a missing file that `BILBO_CONFIG` names is a config error.
- Every `remember` test also needs `HOME` set to a scratch folder, or a config that declares fixture follows: a bare run and a target run that finds the again flag run the follows, and the default follows are the real `~/.claude/projects` and `~/.codex/sessions`.
- Session fixtures in `libs/entries/rust/fixtures/session/` are synthetic, written in the harness's exact field names and nesting; never copy a line of a real session into the repo.
- The `.jsonl.zst` files in `libs/entries/rust/fixtures/session/` are the plain fixtures of the same name packed with `zstd -3 --no-check` (`nix shell --inputs-from . nixpkgs#zstd`: the dev shell has none): pack a plain one again after changing it; a unit test compares each pair.
- `libs/entries/rust/tests/contract/expected.jsonl` is what `build.py` prints, written by `regenerate.py` beside it and never by hand: run it with `--build <the eval's build.py>` after changing `edges.jsonl`, and with `--corpus <unpacked corpus>` to pick `sample.jsonl` again. A line `build.py` stops on cannot go in either file: it belongs in the reader's unit tests.
- `libs/search/rust/tests/contract/expected.jsonl` is what the retrieval eval's bm25 store holds for the spans of `sample.jsonl`, and what bm25s gives for every text there and in `edges.jsonl`, of the folded text, without the words over 4,096 bytes; `libs/search/rust/src/analyze/word.rs` is Python 3.12's `\\w`; `stems.tsv.zst` is PyStemmer's stem of every word of the eval store. `libs/search/rust/src/analyze/fold.rs` is the fold by character over Python 3.12's Unicode data (a character of a non-zero combining class is dropped; a word character whose compatibility decomposition without such characters is all word characters becomes it; every other stays), a `static` written by `regenerate.py --fold` and never by hand; Hangul syllables are computed. `expected.jsonl`, `ranks.jsonl` and `stems.tsv.zst` are what bm25s gives for the folded text: after a change to the fold run `--fold`, then the lines below again. All are written by `libs/search/rust/tests/contract/regenerate.py` (its first lines say how to run it), never by hand: run it with `--store <unpacked eval store>` after changing `edges.jsonl`, with `--corpus` to pick the sample again, with `--table` for the word table, with `--stems` for `stems.tsv.zst`, the stem of every word of the eval store. `libs/search/rust/tests/contract/ranks.jsonl` (bm25s's scores and order) is written by the same script with `--ranks --questions <questions.jsonl>`, and `libs/entries/rust/tests/contract/prefaces.jsonl` by that folder's `regenerate.py --prefaces --corpus <corpus>`: never by hand.
- `recall`'s header and every stderr line it prints are parsed by `evals/retrieval/arms/bilbo-next/search.py` and `check.py`, which stop on a line they do not know: change them with any such line. `derive`'s two lines of standard output and the dry run's `kinds:`, `due:`, `this run:` and `entry` lines are read by `evals/retrieval/arms/bilbo-next/build.py`, which also compares a dry run's whole output with the one before it: change them with it.
- A test of `--in` by words runs an index update after it keeps its files: the label tables are filled by the index run, never by capture or by the store.
- The index folder is bilbo's by its `bilbo-index` file, written before any tantivy file: a test that builds an index folder by hand writes it.
- A test that needs a growth stamp recorded writes its files with an old modification time: `remember` records none for a file written in the same instant.
- A `read` test that needs a page to end or a record to be cut passes `--budget 256`, the smallest: the fixtures fit the default page.
- A test that holds `store.lock` to stand for another writer also holds `store.writer` in the state folder; with `store.lock` alone it stands for a reader, and a bare run waits for it instead of setting the again flag.
- In `apps/cli/tests/derive.rs` every bilbo run is inside the test's process, and a child process holds every open file of that process until it executes, another test's `store.lock` included: a test in which a process is started, by bilbo or by the test itself, holds `alone()`, and one that runs two bilbo runs at once holds `together()` and calls `held_by_the_test()` in the thread it starts. No test sees a mark left out: a busy machine does, at a setup's `remember` that says it waits for another bilbo.
- A test that needs a format 1 store makes one with this tree and writes 1 into the four bytes of a segment's header that hold its format: no binary of this tree writes a format 1 header, and `frame` and `meta` are private to the store, so only their own unit tests call `header_of`.

## Rust

- After changing `Cargo.toml` or `Cargo.lock`, repin with `CARGO_BAZEL_REPIN=1 nix develop -c bazel build @crates//:all`, then run a plain `nix develop -c bazel build //apps/cli` before committing: the repin records `CARGO_BAZEL_REPIN` in `MODULE.bazel.lock`, and only a plain build reverts it. `ureq` brings `ring`, which needs a C compiler where bilbo is built.
- Lint with `nix develop -c bazel build //... --config=lint` (clippy with `-D warnings`, and rustfmt; format with `nix develop -c bazel run @rules_rust//:rustfmt`). Every Rust target sets `lint_config` to the `extract_cargo_lints` target of its Cargo package; without it `[workspace.lints]` silently does not apply.
- A new build script needs an alias of its binary, as `:script` in `libs/language/rust/BUILD.bazel`, or the lint build never checks it. Keep the line of `libs/language/rust/build.rs` that tells Cargo to watch `locales/`, a folder outside its package: no test sees it removed, and Bazel needs none.
- The dev shell has no `cargo`; run it as `nix develop -c bazel run @rules_rust//tools/upstream_wrapper:cargo -- <args> --manifest-path "$PWD/Cargo.toml"`. `cargo test --locked` and `cargo clippy --locked --all-targets -- -D warnings` must pass too: nextest, cargo-mutants and cargo-llvm-cov run through Cargo.
- Keep `BILBO_VERSION` in `tools/bazel/version.bzl` equal to `workspace.package.version` in `Cargo.toml`, and give every target that reads `CARGO_PKG_VERSION` `version = BILBO_VERSION`; nothing checks either.
- A verb's CLI side is the folder `apps/cli/src/<verb>/` (`mod.rs`: its clap `Args` with its page, and `run`; `view.rs`: its human view), registered as one `Verb` variant and one arm in `apps/cli/src/lib.rs`. `kinds()`, `listed()`, `readers()`, `rendering()`, `kind_keys()`, `notes()` (and `Notes`, what it gives) and `apart()`, with the private helpers they call, are the only code that names a kind module; a verb gets what they give as arguments; a new kind joins the first four and, when it declares a key, the fifth. A kind bilbo writes (`note`) has a reader and no `Kind`: it joins `readers()`, `rendering()`, `notes()` and `apart()`. Its logic lives in the library of its domain under `libs/`, never in a crate of all verbs; a new library lists exactly its dependents in the `visibility` of its `:rust` alias. String options use `NonEmptyStringValueParser`, so `--kind=` fails with `--kind needs a value`.
- A child of `libs` is a library named for one thing bilbo does or holds, one level deep: `settings`, `store`, `entries`, `search`, `language`, `llm`, `derive`. It holds one folder for each programming language that implements it (`rust/`), which is the crate: `Cargo.toml` and its `BUILD.bazel` sit there, since Cargo and the Rust rules each take `CARGO_MANIFEST_DIR` from their own file. Files that no programming language owns sit beside it, in a folder named for what they hold (`language/locales/`, `derive/instructions/`). `libs/<library>/BUILD.bazel` only forwards: one alias a language (`:rust`), which dependents name, and a `filegroup` of the shared files where there are any; the real target is visible to that package alone. No test holds this shape. What plugs into one of a crate's contracts is a `pub mod` of the crate that runs it, named for what it binds, a file or a folder (`entries/rust/src/<kind>/` with `entries/rust/fixtures/<kind>/`; `search/rust/src/<tool>.rs` or `search/rust/src/<tool>/`). Inside the crate, `lib.rs` declares the module and only the module and the suites that test it name the tool; outside it, only `apps/` names the module. A module becomes a crate of its own only when some build must leave it out, when it needs a toolchain the rest does not, or when it is a thing bilbo does that more than one library uses. `llm` is the third case: it was `derive`'s until the tags needed a model too, and it took its port and its providers with it. The providers stay modules of the crate that runs them. `language` is a crate for its build step: `build.rs` writes its table, and it has no layout test, since `tools/rust/layout` bans the `include!` that reads it. `libs/derive/rust/build.rs` writes the table of instructions as data, read with `include_str!`: the layout rules ban `include!`. It needs the alias `:script`, as the language crate's does. The five layout tests (`tests/layout.rs` of `libs/entries/rust`, of `libs/search/rust`, of `libs/derive/rust`, of `libs/llm/rust` and of `apps/cli`) hold the module rules above, and a failure says what to change. No guard checks two entries: a new adapter module needs its own in `ADAPTERS` of `apps/cli/tests/layout.rs`, and a new kind a row with no file in `PLACEMENT` of `libs/search/rust/tests/layout.rs`.
- `Lookup` is the read side: `bilbo_search::tantivy::Committed` implements it from segment readers and never calls `Index::reader()`, which creates `.tantivy-meta.lock`. BM25 is `bilbo_search::bm25`, over `Lookup::postings`; tantivy scores nothing. A ranking's two lists count apart: the documents of the kinds a query lists apart, and the rest, each take BM25's three numbers over their own documents, from `holding`, `Lookup::length` and the totals less them, taken off as whole numbers. A document apart moves no other document's score; with no document apart `length` is not asked and every score is the whole index's. What `recall` prints of the main list is then the same hits, order and text as without the documents apart, but for a ref and for where it ends: `Hit::shared_short` is asked of the whole store, so an entry apart that ends in a hit's short id makes that hit's header print the whole id, and a query with no candidate apart gives the main list the room apart too. `holding(Filter::Entries)` takes the whole sorted set, so how a large scope is read is the adapter's alone. `chunk::at` chunks only the passages its coordinates name: a whole entry costs a second; it says whether a chunk opens with its passage's head (`Chunk::headed`), which the index does not hold: the copy rule and the packer leave a hit's first line out only then. A change to the schema changes `FORMAT` in `position.rs`.
- A passage's first piece starts at 0, or after its head: text a chunk holds whole at its start or not at all. Only the note reader gives one, its source line; a reader of another kind that gave one would change what its index holds.
- `Lookup::near` gives terms that live documents hold, each once with its live documents; `typo::distance` (`strsim::osa_distance`: restricted Damerau-Levenshtein over characters) is the definition, held by `typo.rs`'s unit tests, and `the_terms_near_a_word_are_the_ones_the_core_distance_gives_across_segments` holds tantivy's automaton to it for terms of `a` to `z`, the only ones `Bm25` sends: a tantivy upgrade that counts those otherwise fails there. `Bm25` asks for near terms only for a term no live document of the main list holds, which is the whole index when no document is apart, and counts a near term's documents there: a term only documents apart hold is no near term.
- `recall`'s `typos:` line and the log's typos field hold index terms, `a` to `z` only: a change to `typo::Rule::edits` that lets another character through must escape both, and must hold the adapter's distance for such terms, which no test does: only terms of `a` to `z` reach `near` today.
- The bm25s ranking contract runs with `typo::Rule::OFF` and weight 0, on a table that stops the test when `near`, `pairs` or `length` is called.
- `lookup::adjacent` is the one definition of "right after": the adapter and every double that owns its data call it. The core says place for where a term stands in a chunk: `Position` is where an index stands.
- A change to the fold, to its order with `lower`, or to which rule folds changes `analyze::ID` and the catalog's `VERSION`. No test sees every hand edit of `fold.rs`: `regenerate.py --fold --check` does, and no test runs it.
- `Labels` and `Relabel` (`libs/store/rust/src/labels.rs`) are the label tables' read and write sides. Only `libs/search/rust/src/fill.rs` calls `Relabel`, for the entries it read, before the index commits; a catalog made again has no text label until the next index run.
- No write to the label tables before the index commits takes a row from an entry of the store the committed index may hold: nothing empties them, and an entry whose read failed keeps its rows. `recall` at `Current` or `Behind` relies on it.
- `meta.rs` and the SQL of `catalog.rs` are the only code that says origin or parent; everything else says label.
- A change to what a reader's `entry_labels` gives changes its `RENDER`; a change to `analyze::label_words` changes `analyze::ID`: either rebuilds the index and the labels together. Either, and a change to what `fill.rs` files (`analyze::MAX_LABEL_WORDS` is part of it), also changes the catalog's `VERSION`: an older bilbo then makes the catalog again instead of reading rows another rule filed. Nothing checks it.
- `Short::LENGTH` and the header of `apps/cli/src/recall/view.rs` are formats: refs that agents hold depend on them.
- The search core names no engine: under `libs/search/rust/src/`, tantivy, `tokenizers` and whichlang are named in `tantivy.rs`, `qwen/` and `whichlang.rs` alone, and `lib.rs` declares those three modules. `apps/cli/src/lib.rs` builds what they give (`tokenizer()`, `index()`, `lookup()`, `detect()`), as it does for the kinds. A passage over 1 MiB is cut at line ends before it is tokenized (`MAX_ENCODE_BYTES` in `chunk.rs`): one `encode` costs about 180 bytes of memory a byte.
- What bilbo knows about a natural language is one file, `libs/language/locales/<code>.toml`. `bilbo_language` exports the table of those files and nothing else: no function, and no dependency outside the build and the tests. English's 33 stopwords and its stemmer are in no locale file: they are the index's rule and stay in `analyze/mod.rs`. A language's function words leave queries only: `analyze::terms` does not know them, so they change no index and `analyze::ID` stays. A new language needs what admitted Portuguese and no test can ask for: a measurement on real prompts, with every listed language on, since whichlang cannot be narrowed to the listed ones. A detector other than whichlang records `detected` and `not_detected` again in every file.
- The tokenizer is `Tokenizer::encode` with the file's normalizer removed: `encode_fast` and the NFC normalizer each give other tokens than the eval's, and the contract tests fail on either. `libs/search/rust/src/qwen/tokenizer.json.zst` is the pinned `tokenizer.json` packed with `zstd -19`; a unit test checks what it unpacks to.
- A change to the chunker, the analyzer, the stemmer's version or the tokenizer file changes what an index holds: change `analyze::ID` or `bilbo_search::qwen::ID` with it, so an index made before is not taken for current.
- Snapshot baselines in `apps/cli/tests/snapshots/` are plain files: after reading a failing diff, copy the rendered text over the baseline.
- A tunable is a settings key: its default, variable and range live only in its `Key` descriptor, beside the options of the crate that reads it, and `keys()` in `apps/cli/src/console/settings.rs` registers it (a kind's key is handed in from `kind_keys()` in `lib.rs`: `keys` and `load` take it as an argument); a clap flag for a key has no `default_value` and no `env`. The folder keys are the composition root's, in `console/settings.rs`, since more than one crate uses the folders.
- The index position's `failed` line lists the entries a run left out, and `reindex` writes each with the count 1.
- `Reader::appends_only` is the reader's promise that appending records changes no passage already rendered: `Session` answers `true`, `Markdown` `false` (a frontmatter fence closed by a later record turns earlier text into frontmatter), and the index of an entry of a kind that answers `false` is made again whole when it grows. The `Index` port has seven methods, and `position` and `extents` only read: they create, repair and empty nothing. An index grown by `remember` ranks as a rebuilt one, scores included: `a_grown_index_ranks_as_a_rebuilt_one_scores_included` holds it.
- `remember::RECORD_HELD` is an upper bound of what keeping holds for each record beside its bytes (the end `split` gives, what `capture` keeps to pack it). A change to either that passes 64 bytes a record changes it; no test holds it.
- A record of a note entry with no `text` renders nothing. Only `libs/entries/rust/src/note/` defines the note record; a test elsewhere may write one as text. A change to a note's source line, or to which readers' passages stand alone, changes that reader's `RENDER`.
- The identifier `note` stands only in `libs/entries/rust/src/note/`, besides the crate's `pub mod note` line: a test value elsewhere in `libs/entries` or `libs/search` takes another name (`document`).
- Every `derive` test sets the scratch folders, a scratch `BILBO_CONFIG` and `HOME`; the sandboxes point both API endpoints at `http://127.0.0.1:9/` with a dotted key at the top of the file, and a test that makes a call points one at its stand-in. After that key TOML refuses a `[llm]`, a `[llm.<provider>]` or a `[llm.<provider>.api]` header, so a test of the binary writes a provider's `model`, `via` and endpoint dotted; `[llm.anthropic.tool]` and `[llm.openai.tool]` may be headers. A test of a tool way gives a `program`: the default is whatever `claude` or `codex` is on `PATH`. A test of the `codex` way also gives `system_files`, whose default names files of the machine, and a `home` the test made with an empty `auth.json` and set to mode `0700` itself, since bilbo refuses a home its group can write and the dev shell's umask of `0022` hides a test that leaves the mode to the umask; its `program` is a script that answers `--version`, `debug models --bundled` and `exec`. No test starts the real `codex`. No test reaches a real provider.
- `libs/derive` names no kind and no provider: its layout test holds `markdown`, `session` and `note` to no file, so a value there is `notes` or `paragraph`, never `note`. It makes no request and starts no program: it depends on neither `ureq` nor `rustix`, and it names `bilbo_llm` only where it calls a model, the files of the row `bilbo_llm` of its layout test. `libs/llm` names no kind: it depends on neither `bilbo-entries` nor `bilbo-store`.
- Only `libs/derive/rust/src/record.rs` writes or reads a run record. An instruction's id is the hash of its text: an edit of a file in `libs/derive/instructions/` needs no version, and turns `the_shipped_session_instruction_is_the_one_that_was_reviewed` red until the id written in that test is changed with it. That change is where an instruction's edit is reviewed.
- A window is called only when every record before it is covered; `a_window_is_never_called_before_the_records_behind_it_are_covered` holds it. Every record derive spools went through `bilbo_store::opaque::filter` first.
- `ureq` is named in `libs/llm/rust/src/http.rs` alone and `rustix` in `child.rs` alone; only the ways of `libs/llm` and `api.rs` use `http`, `child` and `secret`: an API way and `api.rs` use `http`, `secret` and `child`'s `Bounds`, a tool way uses `child` and `tool`, and a provider's `mod.rs` uses none. `tool.rs` holds what no vendor owns of a tool way, as `api.rs` does of an API way: the parsers and `allowed` texts of the keys both tools' tables have, and `inherited`. The layout row of `tool` covers both vendors' folders, so no test holds that an API way does not name `tool`: `anthropic/api.rs` and `openai/api.rs` each have a variable of that name. `http` follows no redirect, sends a plain `http` request with no proxy, and takes plain `http` only at a literal loopback address.
- An API way is tested against `tools/rust/provider` on a port of this machine, a tool way against a script the test writes. A key in a test is the fixed fake of its suite.
- The response fixtures under `libs/llm/rust/fixtures/<provider>/<way>/` are written by hand in the vendors' field names, never copied from a real answer. A way's request holds no time and no random id and its body's fields are sorted: the eval's cache names an answer by what was sent and never by a key's name. For an API that is the endpoint's address (its scheme, host and port), its path, the headers but the key's and `host`, sorted, and the body; for a tool, its name and what its `--version` prints, the arguments, the variables but `HOME`, `USER`, `PATH` and `TMPDIR`, and standard input. A change to one of those bytes, in `request`, `body`, `invocation` or `inherited` or in a default of `arguments`, `inherit` or `environment`, loses the kept answer of every request it changes.
- A provider is a vendor, a folder `libs/llm/rust/src/<provider>/`: `mod.rs` holds its name, its keys `model` and `via`, the list of all its keys and `model()`, which builds the way `via` names; each way is a file beside it (`api.rs`, `tool.rs`) that implements `Model`. `providers()`, `provider_keys()` and `model()`, with the private helpers they call, are the only code that names a provider module, and they name no way's module; no test holds that. A new way joins its provider's `mod.rs` and the rows of `PLACEMENT`, and no code of `apps/cli` but a sentence of `apps/cli/src/derive/view.rs` that would be false for it (`what` has a tool's words for a cut, a lost login and a spent plan); its keys join every list of the keys: the tests and the snapshots of `apps/cli`, `tests/e2e/cli/config.rs` and `docs/reference/configuration.md`. A new provider joins the three, `ADAPTERS` of `apps/cli/tests/layout.rs` and `ADAPTERS` and `PLACEMENT` of `libs/llm/rust/tests/layout.rs`. Only the `Derive` arm calls `model()`.
- A file a verb keeps under the state folder is opened through `console::private`, beneath a folder the store checked: it refuses a link, a second name, a file that is no regular file and another user's.
- No text of a provider reaches standard error, the log or a run record: a way gives a `What`, a status and identifiers that passed `model::identifier`; `apps/cli/src/derive/view.rs` holds the sentences.
- The eval's `cache.py` keeps what the API ways' tables call the window's or either's: a change to `failed_status` or `completed` of an API way changes `cache.py` and `selftest.py`'s table. Its `told` follows `read` of `anthropic/tool.rs` in the order it takes a refusal, `is_error`, the exit code and `stop_reason`: a change of those changes it and `selftest.py`'s rows.
- The flags of `llm.anthropic.tool.arguments` are read from `claude --help` of 2.1.327: a new one joins the table in `anthropic/tool.rs` with its number of values. `evals/retrieval/arms/bilbo-next/Dockerfile` pins that version: another changes the table, `REPLY` and the pin together, and no kept answer of the eval's tool matches it.
- The arguments of `llm.openai.tool.arguments`, the four fields bilbo sets in a model's entry, the event and item types and the sentences `openai/tool.rs` reads are those of `codex` 0.169.0, from `codex exec --help` and its source at `rust-v0.169.0`: another release changes `RELEASE`, the `doc` of `PROGRAM` (which names the release), the tables and the fixtures together. bilbo asks the program its release at `prepare` and again before each call, and stops at any other; nothing else holds the tables to the release.
- `openai/tool.rs` never opens the login: `home` and `system` read paths and metadata alone (`symlink_metadata`, `canonicalize`, and `read_dir` for a `*`), and no file's contents. No test can hold that.
- A call of the `codex` way is not named by its arguments and standard input alone: the instruction and the model's entry go as two files in the work folder, and the arguments hold their paths. The eval's `cache.py` names no such call, and the arm refuses `openai` by the tool; an arm that takes this way names the two files' bytes.
- What the `codex` way cannot tell is the provider's: a reply it cannot read, an error it does not know and a tool that was reached are `Stopped` with `ServerError`, and the run ends. A cause that is the window's or either's would let a window be charged for the tool's fault; `Stopped` with such a cause does not end a run.
- `SETUP`, `KEPT_OUT` and the default of `system_files` in `openai/tool.rs` are what keeps a user's or a machine's `codex` setup out: a name joins them when a release of `codex` reads a new file from its home, a new variable for its login or its address, or a new file of the machine. `project_root_markers=[]` in `SETTINGS` is what keeps the skills of a git checkout around the work folder out: with no marker `codex` takes the folder it runs in as the project's root. Its switch for skills (`features.skip_host_skill_discovery`) does nothing while its skills extension is installed. No test holds either: both are `codex`'s own.
- `stretches` and its three tests are in `libs/entries/rust/src/tokens.rs`.
- `view::material` escapes its own tags in what it puts in: a change of it or of an instruction changes every request, so the eval's kept answers no longer match.
- `bilbo_entries::tag::apply` is the only code that decides a name's standing for an entry, and `declare` the only code that writes one into a meta that exists: a person's change and a model's are its two arguments. A change of either table of the rule changes its table test, which holds every cell.
- A tag is a stored label. `entry_tags` is filled by the catalog from meta frames, never by the index run, and nothing the index run files holds a tag. A meta frame that differs from the entry's row only in its tags files no change: `a_meta_frame_that_changes_only_tags_files_no_change` and `set_meta_that_changes_only_tags_moves_no_cursor` hold it.
- A tag is compared whole. Words match a tag at query time, from the tags in use: no word of a tag is filed, so a change to `analyze::label_words` needs nothing for tags.
- `Tag::new`, `Tag::MAX_BYTES` and the form `tag:<name>` are formats: configs, skills and agents hold them.
- The meta's field 6 and segment format 2 go together, and a field 6's first byte is the name's standing: a change of what a byte means is a new segment format. A header of either format is read wherever a header is read, and the format reaches `meta::decode` from each walk.
