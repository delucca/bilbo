# Proposal

## Why

bilbo is meant to be installable by people other than its maintainer. Today the only way to get the binary is to clone the repo and run `cargo build` with Rust 1.95 or newer. There are no releases and no Nix package, so dnix cannot install bilbo the way it installs dmacs and trademate either. Every later step depends on a binary that people can actually get: `bilbo setup`, the digest hook, and the cutover from the legacy notes.

## What Changes

- **Releases on tag push.** Pushing a `v<version>` tag that matches `Cargo.toml` runs a release workflow generated by cargo-dist 0.33.0. It publishes a GitHub Release holding:
  - a `bilbo` archive for each target: macOS arm64 and x86_64, Linux x86_64 and arm64;
  - a SHA-256 checksum for each archive;
  - `bilbo-installer.sh`.
- **A one-line install:**
  ```
  curl --proto '=https' --tlsv1.2 -LsSf https://github.com/delucca/bilbo/releases/latest/download/bilbo-installer.sh | sh
  ```
  It installs `bilbo` into `$XDG_BIN_HOME` when that is set, otherwise into `~/.local/bin`. It does not install into `~/.cargo/bin`. Running it again upgrades.
- **A Nix flake in the repo.**
  - `packages.default` builds `bilbo` from the committed `Cargo.lock` and runs the test suite as part of the build.
  - The package ships the plugin and both marketplaces under `share/bilbo/`, laid out as a marketplace the agent tools can add from a local path.
  - `nix run github:delucca/bilbo` works.
  - A dev shell provides the pinned toolchain plus dist. It replaces the `nix shell nixpkgs#cargo …` line in `AGENTS.md`.
- **`bilbo --version`** prints `bilbo <version>`. The installer smoke test and later `bilbo setup` use it to tell which release is installed.
- **Pinned release workflow.** Every action in the generated workflow is pinned by commit SHA through dist's `github-action-commits`, the same rule `ci.yml` follows.
- **Nix build in CI.** CI builds the flake on every PR and every push to main, so a dnix lock bump never finds the flake broken.
- **README.** A `README.md` gains the two install routes.

## Capabilities

### New Capabilities

- `distribution`: how bilbo reaches a machine:
  - the release a tag produces;
  - the shell installer and where it installs;
  - the Nix package and what it holds;
  - the version check between the tag, `Cargo.toml` and the binary.

### Modified Capabilities

- `cli`: a new requirement adds `--version`. Verb dispatch is unchanged.

## Non-goals

- **`bilbo setup` and the home-manager module.** They belong to the next change, add-setup:
  - the store folder;
  - a starter config;
  - the agent plugin installed through the Claude Code and Codex marketplaces at the binary's version;
  - an index timer.

  This change only puts the plugin files where add-setup can reach them.
- **Hook installation.** It waits for add-note-digest.
- **Homebrew, Windows, a PowerShell installer and musl builds.** Each one can be added through dist's config when someone asks for it.
- **Signed releases and installer-side checksum verification.** dist publishes checksums, but its shell installer does not verify them yet. Trust is HTTPS from GitHub.
- **An installer that supports NixOS.** NixOS users take the flake.
- **The dnix side.** The flake input, and adding the package on rivendell, are a dnix commit made after this change merges.

## Impact

- **New files:**
  - `dist-workspace.toml`: dist config, with targets, installers, install path and action pins;
  - `.github/workflows/release.yml`: generated by `dist init` and never edited by hand;
  - `flake.nix` and `flake.lock`;
  - `tests/workflows.rs`: fails on any workflow action not pinned by commit SHA;
  - `README.md`.
- **Changed files:**
  - `Cargo.toml` gains `[profile.dist]`, which dist builds with, and `repository`, which dist needs for GitHub CI;
  - `.gitignore` gains `/result`;
  - `src/main.rs` gains `--version`;
  - `.github/workflows/ci.yml` gains a Nix build job.
- **No new Rust dependency.** The version comes from `CARGO_PKG_VERSION`.
- **New pinned tools.**
  - dist 0.33.0: its version is recorded in `dist-workspace.toml`, and the dev shell takes it from a pinned `nixpkgs-unstable` input, because nixpkgs 26.05 ships 0.31.0.
  - nixpkgs 26.05: provides rustc 1.95.0, which is exactly `rust-version`.
- **`AGENTS.md` updates:**
  - lists the new files and the dev shell;
  - records the release steps: bump `Cargo.toml` and `.codex-plugin/plugin.json` together, merge, then tag.
- **`tests/cli.rs`** gains the `--version` scenarios.
- **Making the Nix job a required check** in the `main pull requests` ruleset is a GitHub setting. It is done only with the maintainer's go-ahead.
