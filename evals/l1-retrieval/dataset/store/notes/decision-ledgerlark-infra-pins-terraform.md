# ledgerlark-infra pins Terraform to 1.9.5

ledgerlark-infra pins Terraform to version 1.9.5. The reason is narrow: the committed provider lock file was produced with 1.9.5, so that is the version the lock file is known to agree with. This note records the decision, the reasoning, and what to do when someone wants to move off the pin. It is written for whoever touches the infrastructure code next, human or agent, and assumes you have not talked to the people who made the call.

Short version: use Terraform 1.9.5 for ledgerlark-infra. Do not bump it as a side effect of another change. If you want a newer version, treat it as its own change with its own review, and regenerate the lock file as part of it.

## Decision

The Terraform version for ledgerlark-infra is fixed at 1.9.5. Every place that runs Terraform against this component uses that exact version: developer machines, the pipeline that plans and applies, and any one-off automation. We chose an exact version and not a range, because a range lets different machines resolve to different binaries, and that is how lock file drift starts.

The decision is about the Terraform CLI binary. It is not a statement about the providers. Providers are pinned separately through the lock file, and the lock file is what ties them to the version we picked.

## Why the lock file drives the pin

The committed provider lock file was generated by Terraform 1.9.5. The lock file records which provider versions were selected and a set of checksums for each. Different Terraform releases can record a different set of checksums, or format entries slightly differently, when they initialise the same configuration. If someone runs a different version, init may rewrite the file, or refuse to proceed, depending on flags and what is cached.

That produces noisy diffs in pull requests that have nothing to do with providers. Worse, it can hide a real provider change inside a pile of checksum churn. Pinning the CLI to the version that produced the file keeps the lock file stable, and keeps any change to it a deliberate one that a reviewer can read.

The pin follows from the lock file. If the lock file is ever regenerated with a different version, the pin moves with it, in the same change.

## What the pin covers

The pin applies to all Terraform configuration in ledgerlark-infra. That includes the resources for the PostgreSQL databases that hold ledger entries and settlement data, the Kafka topics and access rules used to carry settlement events, and the networking and service definitions that the gRPC services sit behind. All of them share one toolchain version so that a plan means the same thing everywhere.

It does not cover application code. The Go services have their own toolchain and their own dependency management. Do not conflate the two when someone says "the version" in a discussion.

## Where the version is declared

The version is declared in the Terraform configuration itself, through the required version setting, so that Terraform refuses to run under a different binary instead of silently proceeding. The same version is also named in the tooling that installs Terraform for the pipeline and for developers, so that the right binary is fetched automatically.

There are therefore at least two places that must agree: the constraint inside the configuration, and the installer setting. If you change one, change the other in the same commit. A mismatch shows up as either a refusal from Terraform or a pipeline that installs a binary the configuration then rejects. Neither is dangerous, but both waste time.

If you find a third place that names a version, such as a container image tag for a build runner, it is a candidate for drift. Align it with 1.9.5 and mention it in the pull request.

## Provider lock file

The lock file is committed to the repository and is treated as source. Reviewers should read changes to it. A change to it should only come from one of three causes: a deliberate provider upgrade, a deliberate Terraform upgrade, or adding support for another platform's checksums.

When the file changes and none of those is the stated purpose of the pull request, ask why. The most common innocent cause is somebody running a different Terraform version locally and committing the result by accident. The pin exists to make that mistake loud.

Do not edit the lock file by hand. Regenerate it with the pinned Terraform, using the normal init and provider lock workflow, and commit the output.

## Local developer setup

Install Terraform 1.9.5 on your machine before working on ledgerlark-infra. A version manager is the easiest way, since it can switch binaries per directory and keep other projects on their own versions. Check the active version before you run init or plan, particularly if you work on several repositories.

If init rewrites the lock file in your working tree and you did not intend any provider change, stop. Check your Terraform version first. Revert the lock file change, switch to 1.9.5, and run init again. Most of the time the diff disappears.

On laptops with different processor architectures, checksums for more than one platform are expected to be present in the lock file. If yours is missing, that is a reason to add platform entries deliberately, not a reason to let a random version rewrite the file.

## CI behavior

The pipeline installs 1.9.5 explicitly and does not use whatever happens to be on the runner image. Plan runs on pull requests and apply runs only from the main branch after review. Both use the same binary, so a plan reviewed in a pull request matches what apply will do.

The pipeline should fail if init would modify the lock file. That check is what turns drift from a quiet annoyance into a visible failure. If you are editing pipeline definitions, keep that behavior. Do not add a step that tolerates or auto-commits lock file changes.

Runner images get updated by whoever owns them. If an update changes the preinstalled Terraform, our explicit install should make that irrelevant. If a pipeline job starts failing right after a runner update, check that the explicit install step still runs before anything else invokes Terraform.

## Upgrading the pin

Upgrading is allowed, just not casual. The sequence we expect:

First, read the release notes for every version between 1.9.5 and the target, looking for changes to state handling, deprecated syntax, and provider protocol changes. Second, make the upgrade on a branch by itself, with no unrelated infrastructure changes. Third, update the required version in the configuration and the installer setting together. Fourth, regenerate the lock file with the new version and commit it. Fifth, run a plan against every environment and confirm it shows no changes that are not explained by the upgrade. Sixth, apply to the least important environment first and watch for state format surprises before moving on.

The pull request description should say the pin is changing and name both the old version, 1.9.5, and the new one. This note should then be updated or superseded, so that it does not keep claiming 1.9.5 after the pin has moved.

## What breaks on a mismatch

Running a different version than the pin usually fails in one of a few ways. Terraform may reject the configuration because of the required version constraint. Init may modify the lock file. A plan may show spurious differences if a different version interprets a resource slightly differently. Or, in the worst case, a newer binary writes state in a form that the pinned version later cannot read.

The last case is the reason to be strict. State upgrades generally go one way. Once a newer Terraform has applied against a shared state, going back to 1.9.5 may not be possible without restoring state from a backup. That makes an accidental apply with a newer binary the most expensive mistake in this area, and it is why the pipeline, not individual laptops, performs applies.

## State file compatibility

Remote state for ledgerlark-infra is shared between the pipeline and anyone allowed to run plans. State is versioned by the Terraform that last wrote it. Keeping everyone on 1.9.5 keeps the state readable by everyone.

Before any upgrade, take a backup of state for each environment, and confirm you know how to restore it. Plans are read-only with respect to resources, but check that your backend does not take locks in a way that blocks others during a long investigation.

If you ever find state that was written by a newer version than the pin, do not apply against it. Raise it with whoever owns the infrastructure, work out which run wrote it, and decide whether to move the pin forward or restore.

## Alternatives considered

We looked at a version range, such as allowing any release in the same minor line. It would reduce friction when patch releases come out, but it brings back the drift between machines, which is the problem the lock file is meant to prevent. Rejected.

We looked at not committing the lock file. Then providers would float and every init could pick a different provider version. For infrastructure that holds the databases and messaging behind financial reconciliation, unreviewed provider changes are not acceptable. Rejected.

We looked at always tracking the latest Terraform. Rejected for the state compatibility reasons above and because finance operations teams depend on this infrastructure being boring.

We chose to pin exactly, pin to the version that generated the lock file, and upgrade deliberately.

## Risks and tradeoffs

Pinning means we do not get newer Terraform features or bug fixes automatically. If a fix we need lands in a later release, we have to do the upgrade procedure above. That is a cost, and we accept it.

Pinning also means a security issue in the Terraform binary needs a prompt, planned upgrade. Someone should watch release announcements, and a security-driven upgrade can skip the usual patience but not the checks: still separate branch, still regenerate the lock file, still plan everywhere.

There is a smaller risk that people forget the pin exists and fight it. The required version setting and the pipeline check are there so the failure message points them back here.

## Modules and environments

All environments share the same pin. We do not allow one environment to run ahead on a newer version, since then a change tested in one place would not be representative of the others. If a staged rollout of an upgrade is needed, do it within a single upgrade branch and a single sequence of applies, then merge once all environments have moved.

Shared modules inside the repository inherit the pin. If a module is ever extracted and consumed elsewhere, give it a version constraint that is a floor and not an exact match, and leave the exact pin to the root configuration that consumes it.

## Interaction with Kafka, PostgreSQL and gRPC resources

The resources most sensitive to an unplanned change are the PostgreSQL instances and the Kafka topics. A spurious diff on a database or on a topic's retention and partition settings could be destructive or could disturb consumers that process settlement events. This is a practical reason to keep plans trustworthy, and a trustworthy plan starts with a stable toolchain.

For gRPC-facing services and their load balancing or certificate resources, a changed provider default can alter behavior in ways application tests will not catch. Provider versions are held by the lock file, which in turn is why the lock file and the Terraform version are kept together.

## Review checklist

When reviewing a pull request in ledgerlark-infra, check these things. Does the lock file change, and if so is a provider or Terraform upgrade the stated purpose? Does the required version in the configuration still say 1.9.5, and does the installer setting agree? Does the plan output show only the changes the description promises? Did the pipeline's init step pass without rewriting anything?

If the answer to any of these is unexpected, ask before approving. Reviewers should not approve a lock file change on the grounds that the pipeline is green; the pipeline can be green with the wrong provider.

## Open questions

We have not settled who watches Terraform release announcements and owns the upgrade cadence. Until that is decided, upgrades happen when someone needs a feature or when a security notice forces it.

We have also not decided whether to automate a periodic check that proposes an upgrade branch. It might help, but it risks encouraging casual bumps. If someone builds it, it should only open a branch and never apply.

Another open point is whether developer machines should be prevented from applying at all. For now the convention is that applies come from the pipeline.

## Notes for agents

If you are a coding agent working in ledgerlark-infra, do not change the Terraform version, the required version setting, or the lock file unless the task explicitly asks for an upgrade. If your local Terraform is not 1.9.5, say so and stop or install the right one; do not work around it by loosening the constraint.

If a command you ran changed the lock file unexpectedly, revert that change before committing, and mention it in your summary. When writing new Terraform here, assume 1.9.5 syntax and features only.

If a task seems to need a newer feature, report that to the user and propose the upgrade procedure above as a separate piece of work. Keep this note current if the pin ever changes.
